# 03 · 支付与交付对账工具

PRD 1.0 · 2026-10-18 · 运行基础设施 · 第一批候选  
状态：设计提案，未实现/未付款/未提交。先读[总体接入设计](../总体接入设计.md)与[接口事件约定](../接口与事件约定.md)。

## 1. 用户与真实场景

**用户：**经营付费 API 的团队，以及需要核查自己 Agent 调用结果的账户所有者。

**第一次使用：**用户反馈“付钱了但没有文件”。运营输入业务请求 ID，看到业务计算已完成、结算已确认、响应丢失，随后恢复原文件访问，而不是再让用户付款。

**问题：**业务日志、Passport 执行响应、活动记录和交易凭证分散。仅看余额或交易数量无法判断具体交付，也容易把延迟、重复调用和真正失败混在一起。

**Kite 接入价值：**补齐支付与应用交付之间的证据关联。不是新的区块浏览器；不声称付款一定只有一笔链上转账，也不把时间/金额相近视为确凿匹配。

## 2. MVP 范围

**P0，首版必须完成：**

- 接入自有卖方事件日志；买方可在自己授权的上下文导入 session execute 结果与 kpass activity。
- 确定性关联 operation_id、merchant_request_id、receipt/reference、产物哈希；不确定匹配进入人工核查队列。
- 展示付款、业务执行、响应发送和结果访问四条状态，不合成一个含糊 success。
- 生成异常处理单：恢复结果、等待凭证、联系服务方、人工退款待处理；不自动转账。

**P1，有真实反馈后再做：**

- 增加按项目、服务、网络的费用和异常分析。
- 在有稳定来源时添加只读链上凭证适配与告警；非自有用户活动不可越权抓取。

**首版排除：**不重新做钱包，不从公共链推断用户全部 Passport 活动，不依据一次余额变化自动退款。

## 3. 完整用户流程

1. 卖方 SDK/服务按公共事件契约写日志，业务请求携带 operation_id。
2. 买方自行导入执行响应或使用已授权只读适配采集活动。
3. 关联器按强证据建立关系；只有时间/金额相似则提出候选。
4. 运营查看异常，区分未付款、付款未知、已付未交付、已交付响应丢失。
5. 按现有权利恢复产物或登记人工处理，保留操作者和原因。
6. 后续证据到达时更新当前结论，历史判断不可覆盖。

## 4. Kite 能力接入

| 官方能力 | 接入方式 | 保存与验证 |
|---|---|---|
| 付款证据 | session execute 响应与 payment_receipt/reference | 字段以实际输出为准；多协议不假定固定 transaction_hash 顶层字段 |
| 活动来源 | kpass activity --kind x402_payment --output json | 仅当前授权用户，可分页但按采集窗口与游标去重 |
| 卖方证据 | facilitator 结算响应与业务事件 | 可见交易状态、merchant_request_id、产物摘要；无权限数据标缺失 |

**接入前置：**所有涉及真实付款的路径先完成 G0，固定 network/asset/facilitator/CLI/账户环境；见总体接入设计。真实身份或 Runtime 不可得时明确 blocked，不能用 mock 替代。

**授权边界：**应用与业务权限自己验证；Passport 的 passkey 批准保留给真实用户；本轮 PRD 编制不发起任何授权或支付。协议实例、金额、会话和示例均以现场预检与实际输出为准。

## 5. 接口与数据

**拟提供接口：**POST /imports/executions、POST /imports/merchant-events、GET /operations/{id}、POST /cases/{id}/resolve。全部是本项目自建鉴权接口，不是 Passport 官方 API。字段无法取得时返回 missing，不伪造关联。

**核心对象：**Operation、ExecutionAttempt、SettlementEvidence、ArtifactEvidence、DeliveryObservation、MatchDecision、Case、ResolutionEvent。一个 operation 可关联多次尝试和多个交易参考。

operation_id、付款证据、业务版本及产物按公共事件契约关联。接口/包名属于本项目设计，不代表官方已经发布同名能力。

## 6. 状态与恢复

付款：NOT_ATTEMPTED/PENDING/CONFIRMED/UNKNOWN/FAILED；交付：NOT_STARTED/RUNNING/READY/SENT/ACCESSED/FAILED。异常由组合规则产生，不能用单一线性流程抹平。

- 钱包余额只作辅助展示，不作为结算证明；导入文件缺字段时降级为证据不足。
- 同一交易被重复导入不重复计费统计；一对多/多对一关系允许存在，必须保留来源。
- 人工退款只登记动作与证据，完成与否根据真实凭证确认；产品不在后台持有支出权限。

任何付款未知均不能通过换 key 自动重买；任何产物恢复都需要原权限。测试桩中的假付款不产生真实交付承诺。

## 7. 开发任务拆分

- 03-T01：定义事件和关联强度，制作故障样例集。
- 03-T02：实现卖方事件导入与买方授权导入。
- 03-T03：实现关联器、异常分类和人工核查。
- 03-T04：实现结果恢复入口与追加式审计。
- 03-T05：联调一个真实付费服务，交付部署与排障手册。

**投入粗估：**5–7 人周。先做 M0 兼容与样本验证，再做独立核心、真实互通及发布；外部批准、环境开通和审核不计入可承诺工期。

## 8. 界面与使用体验

订单式对账台，上方按 operation 搜索，下方并排展开付款证据与交付证据；醒目标注未知与候选匹配。

在需要用户决定时展示价格、范围、权限和失败状态；普通产品页面不堆协议实现细节，技术证据留在诊断/报告页。

## 9. 验收与演示

下面是目标，尚未运行或达成。

- A01：包含响应丢失、重复导入、付款未知、部分交付和多交易参考的标注数据逐项可解释。
- A02：无 operation/receipt 等强证据时不自动确认匹配。
- A03：同一付费调用的真实卖方与买方证据可关联，缺失侧如实标出。
- A04：导入隔离、权限检查、追加审计和敏感字段清理可验证；数据迟到不会覆盖历史。

**完整演示：**构造一次真实付费后的响应丢失，导入双方记录后恢复原结果；再展示一个金额相同却不能确认匹配的案例。

**试用观察：**人工定位一次交付异常所需时间、待核查积压、误匹配率和用户重付事件。

## 10. 提交与独立性

开发/运行工具贡献，需核对实际提交类别。可与付款 SDK 配套使用，但独立交付是关联引擎与核查流程。

项目核心包括本 PRD 定义的模型、业务引擎/状态/断言与样本；支付和基础依赖可正常共享，不复制其他参赛实现换名。EC 映射、活动审核与真实贡献是否被统计分别跟踪，不用本 PRD 保证收录。
